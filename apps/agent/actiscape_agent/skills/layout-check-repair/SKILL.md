# 检查与有限修复

> v1 接入说明：本 Skill 只声明语义 capability，不能直接写正式场景、提交项目或执行任意脚本。所有修改必须形成候选，并由固定代码预检、渲染、审核和提交。

## 什么时候用

✅ 适用：

- 场景里已经有一版布置（用户自己摆的、或上一个技能产出的），需要判断"哪里不对"；
- 用户说"门怎么开不开""这个柜子能不能放这""能不能自动帮我修一下"；
- 内层 harness 跑完一次设计，要做交付前的自检与收尾。

❌ 不适用（转其他技能或交回主控）：

- 还没有布置：先跑对应的场景技能，别用本技能从零摆家具；
- 需要拆改墙体、门窗洞口：超出范围，交回主控；
- 用户明确要求"改到通过为止"：本技能按 3 轮预算执行 [J-VER-02]，做不到就如实说做不到。

开工前只确认三件事：

1. 场景版本号（所有修改都要带 `base_version`，避免覆盖用户操作）；
2. 哪些对象是用户指定要保的（保的对象只动位置，不删不改尺寸）[J-VER-01]；
3. 修复预算几轮（默认 3 轮 [J-VER-02]）。

## 怎么做

**第 1 步 · 先检查，再动手**
`scene.read` 取当前版本，直接 `candidate.preflight / candidate.review`。**不要先改再检查，也不要先看效果图**——
效果图不告诉你"门前没有落脚点"，检查报告会。

**第 2 步 · 排序（决定先修哪一条）**

1. `severity = error` 优先，`warn` 最后；
2. 同级按 `object_ids` 数量降序——影响对象越多，越可能是一处错位带出一串问题；
3. 再按"是否挡门/挡通道"优先（门被挡 = 整个房间的功能失效）；
4. 排序结果写进交付，让用户看得见"为什么先修这条"。

排序示例（同一次 `candidate.preflight / candidate.review` 报了 4 条）：
`DOOR-02`（2 个对象，挡门）→ `OVER-01`（2 个对象）→ `WIN-01`（1 个对象）→ `CIR-02`（整室比值，warn）——
先修"门"，因为门不通，后面所有判断都没有意义。

**第 3 步 · 定位（一句话说清）**
每条 issue 都翻译成"对象 + 位置 + 违反了什么"，例如：
"茶几 `o_coffee` 在 (3300, 4300)，压住了东门 900 门扇的扫掠区"。
只说码不说位置，用户没法判断要不要接受这个修法。

**第 4 步 · 一次只修一类**
"同类" = 同一个 `code`。一轮里只处理一个 code 的所有 issue：

1. 规划最小改动（能移就不删，能删就不换）[J-VER-01]；
2. 一次 `candidate.propose + candidate.preflight`，带 `base_version` 与唯一 `op_id`；
3. 立刻重跑 `candidate.preflight / candidate.review`，对比"这一类是否清零、有没有带出新的 error"。

| 码        | 判据                | 典型情形                   | 有限修复动作                                   |
| --------- | ------------------- | -------------------------- | ---------------------------------------------- |
| `DOOR-02` | J-DOOR-02           | 门扇扫掠区有家具           | 移出扫掠区；改成推拉门属越界，只写进未解决清单 |
| `DOOR-01` | J-DOOR-01           | 推拉/折叠门前 400 有家具   | 沿墙平移                                       |
| `CUR-01`  | J-CUR-01            | 窗帘区 150 内有高家具      | 降高到 600 以下或移走                          |
| `WIN-01`  | J-WIN-01            | 窗前 400 有高柜            | 换矮柜或移到侧墙                               |
| `OVER-01` | J-OVER-01           | 两件落地家具重叠           | 推离 50 以上，保留桌椅/边几例外                |
| `CIR-02`  | J-CIR-01 / J-CIR-02 | 门到不了主要区域、通行不足 | 收窄或移开占道的家具                           |

**第 5 步 · 什么时候判"修不动"**
出现下面任一情形就停，不要继续试：

1. **空间不够**：移开 A 就必然压住 B，房间尺寸本身不支持（报 `E_CONSTRAINT_UNSATISFIABLE`）；
2. **修它会引起更严重的问题**：为了过门扇检查把沙发删掉，功能就没了；
3. **需要用户决策**：涉及改门、改墙、换家具品类、加预算。

**第 6 步 · 如实报告（这是本技能的产出，不是免责声明）**
交付必须同时给三张清单：

1. **已解决**：code + 对象 + 改了什么（位置从 → 到）；
2. **未解决**：code + 对象 + 为什么修不动 + 需要用户做什么（越界项写明"需人工/需改硬装"）；
3. **剩余风险**：没被检查覆盖的项（比例、风格、照度）明确标注"未经工具检查"。
   3 轮预算用尽仍未清零的，全部进"未解决"清单 [J-VER-02]，**不得把未解决项从报告里删掉**。

| 分区     | 内容                                | 必填 |
| -------- | ----------------------------------- | ---- |
| 已解决   | code / 对象 / 从 → 到               | 是   |
| 未解决   | code / 对象 / 原因 / 需要用户做什么 | 是   |
| 剩余风险 | 未覆盖的判据（比例、风格、照度）    | 是   |
| 证据     | 修复前后平面图 + 版本号             | 是   |

**第 7 步 · 三条红线**

1. 不修改验收规则、不删检查项、不降低阈值来"通过"——这是造假，不是修复；
2. 不静默删除家具：删除必须写进"已解决"并说明替代方案；
3. 不把 `warn` 当 `pass`，也不把 `pass = true` 说成"完美"——它只代表没有 error 级几何问题。

三条红线任何一条被打破，本次修复即判失败，并在交付里写明打破了哪一条。

## 依赖什么

| 工具                                      | 用途                            | 状态    |
| ----------------------------------------- | ------------------------------- | ------- |
| `candidate.preflight / candidate.review`  | 拿 issue 列表；每轮复跑对比     | 可 mock |
| `scene.read`                              | 取当前版本与对象坐标            | 待成员1 |
| `candidate.propose + candidate.preflight` | 提交修复动作，带版本与幂等      | 待成员1 |
| `candidate.review`                        | 证明只改了该改的对象 [J-VER-01] | 待成员1 |
| `candidate.render`                        | 修复前后各出一张平面图作证据    | 待成员1 |

与原项目 Skill 的差异：原流程是"脚本自查 → 人工看图 → 再生成"，没有预算概念；本技能把修复写成**有轮次上限、有排序规则、有未解决清单**的流程，判断可追溯。

未适配时的降级路径（状态仍为 `pending_adaptation`）：

- 没有 `candidate.preflight / candidate.review`：按判据表人工逐条核对（门扇、窗帘区、窗前 400、重叠、通行），在报告里注明"人工核对"；
- 没有 `scene.*`：只输出 issue 清单与建议动作，不执行修改；
- 没有 `candidate.render`：用坐标表代替截图作证据。

## 怎么验证

- **正向** `LCR-dev-01`：3.8 × 5.4m 起居室，初始状态里沙发横在门口、茶几正对门洞。第 1 轮清门（`DOOR-02` 清零），第 2 轮复位茶几并补地毯，第 3 轮前 `candidate.preflight / candidate.review` 已全通过。期望 `pass = true`。
- **边界** `LCR-dev-02`：3.6 × 4.2m 书房，初始状态有"门口堆着桌子椅子"与"窗下 2400 高柜"两类问题。3 轮里只够修门与入口通行，窗下高柜（`WIN-01`）未处理，预算用尽。期望 `pass = false` 且 `must_trigger = WIN-01`——**这就是"如实报告未解决"的形态**。
- **反向校验**：把 `LCR-dev-02` 的期望改成 `pass = true` 应该失败。如果它能"通过"，说明流程里混进了"改规则凑结果"的做法。

两个案例在 `examples/` 下，`ops.json` 可被 mock 引擎复跑；L1 结构与 L2 几何结果记录在 `manifest.validation`。
