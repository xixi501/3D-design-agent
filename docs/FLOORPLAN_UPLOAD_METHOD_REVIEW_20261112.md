# 户型图上传：现状与问题

日期：2026-11-12  
范围：真实户型图上传能力的现状记录，不包含方案建议。

## 一、我们要做什么

产品目标是让用户把自己的真实户型带进设计工作台，并继续完成：

```text
上传真实户型
→ 建立墙、门窗、房间
→ 编辑家具
→ 检查
→ AI 修复或人工调整
→ 保存、重开、导出
```

上传只是入口，真正的产品能力在后续编辑、检查、修复、家具和交付。

当前对上传结果的验收级别没有正式定义。实际出现过几种不同说法：

- 能生成初步结果；
- 能打开草稿面板；
- 能通过预览；
- 能生成可确认草稿；
- 能全自动完成。

这些级别没有被统一，导致同一个结果有时被当作进展，有时被当作失败。

## 二、参考了哪些方法

### house-plan-designer

- 仓库：https://github.com/ZWD11/house-plan-designer
- 方法：OpenCV 提取墙线、断口、尺寸刻度，生成初稿；Agent 对照原图补墙、补门窗、补尺寸；再做尺寸链定位和墙体对账。
- 事实：它不是一次全自动。README 的实测中，21 面墙有 8 面由 Agent 补全；文档明确说明识别会漏墙，门窗类型也只是猜测。

### OpenBIM FloorPlan AI

- 仓库：https://github.com/Chunling1/OpenBIM-FloorPlan-AI
- 方法：UNet + ResNet34，语义分割墙、窗、门；CubiCasa5K mIoU 0.787。
- 输出是像素 mask，不是可直接编辑的墙体几何。

### Floor Plan to BIM

- 仓库：https://github.com/Mr-Daker/Floor-Plan
- 方法：SegFormer/Mask2Former 语义分割，OpenCV/Shapely 矢量化，IfcOpenShell 导出 IFC。
- 报告指标：约 80.96% mIoU，wall IoU 约 81.61%；作者指出细墙、门、窗仍是最敏感的类别。

### HEAT

- 论文：https://ar5iv.labs.arxiv.org/html/2111.15143
- 方法：输入栅格图，检测角点与边候选，端到端重建平面图，不依赖墙 mask。
- 代表“结构化重建”路线。

### FloorPlanFormer

- 论文：https://ojs.aaai.org/index.php/AAAI/article/view/37625
- 方法：多任务 Transformer，同时识别入口门、外轮廓（墙/窗）和内轮廓（房间类型）；构建 FloorPlan8K 数据集。
- 说明只做墙 mask 不足以覆盖房间和门窗语义。

### 其他基础

- R2V / Residential Floor Plan Recognition and Reconstruction（CVPR 2021）：栅格到矢量的平面图重建路线。
- CubiCasa5K：常用的户型图语义分割数据集。

## 三、目前做到哪里

| 能力 | 状态 | 说明 |
|---|---|---|
| GPU 推理环境 | 可用 | RTX PRO 6000 Blackwell |
| Qwen3-VL-32B 视觉服务 | 可用 | `visionAvailable=true`，真实调用成功 |
| OpenBIM 分割模型 | 可运行 | 墙/窗/门 mask 与叠加图已生成 |
| 视觉失败时保留草稿 | 已合并 | PR #6 |
| 结构候选恢复 | 部分可用 | 原始墙段不足时改用 HPD 原始候选 |
| 尺寸比例检查 | 部分可用 | 横纵比例不一致时会拒绝，不静默拉伸 |
| wallaudit 接口 | 可用 | 对人工修复后的受控草稿返回 0 处不一致 |
| 真实图端到端上传 | 未通过 | 仍卡在结构补全/几何绑定 |

### 验证到的具体结果

- 用户提供的 919×1024、9600×10800 户型图，图本身比例合格；
- HPD 直接分析得到 22 段墙、9 个断口；
- 横向比例 14.393，纵向 14.439，差约 0.3%；
- 但 HPD 像素候选漏掉完整外墙；
- 结构模型只能选到碎墙段；
- 最终报“无法把全部已读尺寸绑定到实测墙面”。

### OpenBIM 分割结果

- wall 像素：57643；
- window 像素：15364；
- door 像素：6126；
- 分割叠加图能覆盖外墙。

分割可用，但尚未转成墙体几何候选。

### Qwen 纠错 pilot

Qwen 读取原图、分割叠加图和当前草稿墙线叠加图后，能输出 6 条缺失外墙，坐标沿真实外轮廓，避开了图片白边。

应用后：

- 尺寸绑定错误消失；
- 预览仍提示“发现未连接墙端”；
- 未能进入 wallaudit。

目前只验证了“VLM 能提出补墙”，没有接入产品草稿面板。

## 四、目前的方法

当前实际采用的是混合路线：

```text
HPD 像素墙线/断口/尺寸候选
→ 结构模型从候选里选择墙、门窗、房间
→ TypeScript 几何编译与检查
→ Qwen 视觉模型做家具/语义辅助
→ OpenBIM 分割作为补充证据
```

这条路线目前存在以下事实：

1. HPD 候选会漏外墙，或把一面墙切成多个碎段；
2. 结构模型只能在候选里选，不能生成缺失墙；
3. 分割 mask 更完整，但没有被直接矢量化，只是作为叠加证据或贴回图片；
4. VLM 能提补墙建议，但补墙后没有确定性几何清理；
5. 测量锚点、测量特征、业务墙和洞口分属不同表示，容易失去绑定；
6. 各环节没有统一的中间表示，也没有统一验收标准。

## 五、方向上的问题

### 1. 产品定位未定

当前无法确定上传功能服务于哪类产品：

- 如果是设计产品，上传做到辅助导入即可，失败可以 CAD、手动补墙或空白新建；
- 如果是识别产品，则需要分割、矢量化、拓扑优化、尺寸校准和真实图基准集。

目前的实际要求更接近识别产品，但产品主体是设计工具。

### 2. 自动化级别未定

“可识别”“可核对”“可确认”“可自动”没有正式定义，也没有对应验收。

因此同一张图的结果，既可能被称为“已经能打开草稿”，也可能被称为“上传失败”。

### 3. 技术路线未固定

在 HPD 规则/CV、语义分割、VLM 纠错、手工补墙、CAD 矢量之间反复切换，缺少固定基线，无法比较哪条路线更有效。

### 4. 缺少统一的户型结构表示

目前同时存在：

- 像素 mask；
- HPD 墙段；
- 业务墙；
- 草稿墙；
- 测量特征；
- 锚点；
- VLM 操作。

这些不是同一个结构，转换时会丢失信息。

### 5. 缺少确定性几何清理层

从“VLM 建议”到“可确认草稿”之间需要：

- 墙端吸附/延伸；
- 共线合并；
- 去重/去碎墙；
- 房间闭合；
- 洞口归属；
- 尺寸校准；
- wallaudit 对账。

目前这些没有形成完整闭环；一次 VLM 补墙不能解决。

### 6. 缺少真实基准集

当前多用单张图或少数图判断好坏，没有统计：

- 墙体召回/精度；
- 门窗召回/精度；
- 房间闭合率；
- 尺寸误差；
- 人工修正量；
- 从上传到可确认草稿的耗时。

### 7. 图像上传占用产品精力过多

上传是入口功能，但实际投入了大量时间在墙线参数、候选合并、mask 后处理和补墙。编辑、检查、修复、家具和导出的投入被挤压。

## 六、现状结论

- 视觉模型可用；
- 分割模型可用；
- VLM 能提出补墙；
- 但真实图上传仍未到“可确认草稿”；
- 墙端闭合、房间闭合、洞口归属、尺寸绑定和 wallaudit 尚未形成端到端闭环；
- 目前仍无法把上传能力定义为已完成。

根因不在单点模型能力，而在于：

1. 上传功能的验收级别没有定清；
2. 没有统一的户型结构中间表示；
3. 没有确定性几何清理层；
4. 没有真实图基准集；
5. 上传功能占用了过多主产品精力。
