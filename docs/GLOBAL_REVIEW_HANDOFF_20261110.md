## 2. 项目最终目标

项目书 v1.1 的正式定位：

> 面向希望自行表达和调整居住空间方案的普通用户，以
> house-plan-designer 为基础，建设可持续对话、可编辑和可漫游的多 Agent 室内场景设计系统。
> 首版围绕住宅客餐厅，支持从户型图或文字需求形成三维房间，并将用户拍摄的自有物品转为
> 独立三维模型加入方案。

最终目标不是：

- “只要任意户型图都能全屋自动识别”；
- “做一个完整的通用单层住宅 CAD 系统”；
- “训练最强户型视觉模型”；
- “Agent 数量越多越好”；
- “把所有 Skill 都接入才叫完成”。

这些可能是阶段技术路线或后续扩展，但不能替代项目书定义的产品目标。

### 2.1 用户价值

项目重点降低：

- 初稿制作负担；
- 物品摆放预览负担；
- 反复修改和沟通成本；
- 用户表达自己家具、摆件和空间偏好的门槛。

用户应能：

- 保留自己的家具和摆件；
- 查看尺寸、颜色和位置关系；
- 通过语言或直接操作调整方案；
- 在三维中漫游和检查；
- 保存后继续修改。

项目书明确要求：制作时间、修改成本、人工干预改善必须有实际记录，不能预设节省比例，
也不能用功能数量代替效果证明。

## 3. 核心用户闭环

项目书定义的主体验：

```text
输入户型图或文字需求
→ 生成三维房间
→ 对话或手动编辑
→ 上传自有物品照片并放入房间
→ 漫游查看
→ 保存并继续修改
```

典型流程：

1. 用户给出客餐厅户型和家具需求。
2. 系统生成初稿。
3. 用户说“只调整阅读角，保留餐桌与门窗”。
4. 系统修改指定区域，不破坏无关对象和结构。
5. 用户上传一个花盆照片，确认外观和尺寸。
6. 用户点选茶几，或说“放到这张茶几上”。
7. 系统检查支撑、越界和明显穿插。
8. 用户移动、撤销、保存并重新打开。

产品主闭环是“设计、修改、自物入场、检查、漫游和持久保存”。
户型识别只是入口之一，不是整个产品的中心。

## 4. 首版范围

| 范围 | 项目书约定 |
| --- | --- |
| 主场景 | 住宅客餐厅 |
| 输入 | 文字需求、清晰户型图 |
| Agent 编辑 | 家具、摆件、材质和布局；已有墙、门窗默认保持 |
| 人工编辑 | 保留人工结构编辑工具，可在草稿上修正 |

| 资产操作 | 尺寸确认、点选落点、自然语言指定已知对象 |
| 场景来源 | 本项目数据和 house-plan-designer 结构化项目 |
| 改进机制 | 内层 harness；主流程稳定后接 GEPA 外层对照 |
| 不进入首版 | 报价、施工图、水电、智能家居演示、物理仿真、机器人训练、整屋照片精确重建、复杂照片分割 |

首版不需要：

- 任意房型零校正；
- 任意图纸样式；
- 全屋家具自动识别；
- 多层和曲线墙；
- 任意外部 GLB 房间语义恢复；
- 完整地震模拟或刚体动力学。

这些能力以后可以扩展，但不能反过来改变首版验收。

## 5. 项目真正新增的贡献

项目书要求区分：

- 原项目已有能力；
- 已核查基础；
- 本项目拟开发能力；
- 后续扩展。

不能把 house-plan-designer 原有编辑、漫游、GLB 导入或 Three.js 渲染说成 ActiScape 新成果。

本项目的主要新增贡献应是：

1. 保留前端功能的全面模块化重构；
2. 可持续对话和手动操作共同编辑同一场景；
3. 用户单件照片转为独立 3D 资产并放入已有场景；
4. 对指定对象、数量、支撑关系、局部影响和版本一致性进行检查；
5. 可人工维护、适配、版本化和真实验证的 Skill 池；
6. 内层可靠执行和后续 GEPA 外层最小对照；
7. 三人模块、真实工作台和 AgentArts 的完整集成。

判断项目是否成功，应优先看这些新增能力是否形成端到端用户价值，而不是看识别模型或 Agent
架构有多复杂。

## 7. 项目书中的 Agent 设计

原始产品设计是一个主控加三个专职 Agent：

| 角色 | 职责 |
| --- | --- |
| 主控 Agent | 理解需求、选择 Skill、分配工作、管理进度、汇总结果 |
| 空间设计 Agent | 家具布置、局部编辑、选择落点 |
| 资产 Agent | 选择现有资产、处理照片、调用建模、整理尺寸材质 |
| 检查 Agent | 几何、需求、渲染和对象定位检查 |

原则：

- 简单移动不需要所有 Agent 参与；
- 数量、尺寸、吸附和几何检测优先使用确定性工具；
- 模型负责需求理解、方案选择和综合审核；
- 检查失败后根据证据交回负责角色；
- Agent 的“成功”描述不能替代工具执行和检查证据。

当前仓库为了全屋户型识别，已经扩展出：

- main；
- structure；
- vision；
- assets；
- design；
- check；
- 固定代码 Coordinator。

这是实现层扩展，不是项目书原目标。新评审必须判断：

- 这种扩展是否解决真实产品问题；
- 是否为了不成熟的自动识别拖走了本应投入 S3-S5 的资源；
- 是否可以用更少角色和更清晰的固定服务完成同样边界。

## 12. 当前技术架构概要

### 12.1 主场景链路

主系统采用：

```text
用户输入
→ 任务与角色编排
→ 候选场景修改或 SceneDraft
→ 确定性检查
→ 渲染/截图/WebGL 证据
→ 审核与有限修复
→ 按 revision 一次原子提交
→ 保存、撤销和恢复
```

### 12.2 通用场景底层

为后续扩展定义了：

- `InputBundle`
- `EvidenceGraph`
- `IntentSpec`
- `SceneDraftDocument`
- `SceneProposal`
- `SceneProgram`
- `AssetResolution`

设计意图：

- 所有输入可追溯；
- 文字只产生意图，不伪造图片证据；
- 户型图和项目导入提供结构事实；
- 草稿与正式项目分离；
- 所有 Agent 修改通过同一候选和提交入口。

这符合项目书“统一场景快照、对象身份、版本和提交”的要求。

需要审查的是实现规模是否合适、是否过早，而不是因为名称现代就默认合理。

### 12.3 多 Agent 扩展

当前 V4 使用固定代码 Coordinator 控制阶段、权限、预算和修复。

优点：

- 防止 Agent 自由互聊；
- 防止模型越权提交；
- 角色上下文最小化；
- 失败可追溯；
- 模型不能扩大修复预算。

风险：

- 角色过多；
- 维护成本高；
- 先建复杂架构再补真实能力；
- 与项目书四角色模型不完全对应；
- 顶层产品主控 Agent 与固定代码 Coordinator 的职责需重新说明。

### 12.4 视觉 Provider

Provider 是工具进程，不是 Agent：

- 返回像素空间候选证据；
- 不写正式场景；
- 不读评估参考；
- 失败不自动换 Provider。

当前唯一登记的结构 Provider 是实验性的 HPD 包装。

原因不能简单概括为“DeepSeek 不会 3D”：

1. HPD 是半自动初稿工具，不是全屋通用识别器；
2. 当前 V4 墙掩膜和候选过滤可能漏掉黑色实心墙，并把家具或短边当墙；

4. VLM 只能从候选中选择，不能恢复不存在或严重错误的几何候选。

但这些原因只解释 V4，不直接决定项目下一阶段。必须先回答 V4 与项目目标的关系。

必须保留并解释，不能删除或计入通过。

### C. 离线回放

只证明冻结输入下逻辑可重复，不证明真实视觉泛化或用户价值。

### D. 契约和架构测试

只证明边界、schema、权限和持久化，不证明业务任务完成。

### E. 无效/降级证据

只能用于调查，例如：

- reference 进入候选结构的 oracle-assisted V4；
- 测试替身；
- 未提交 mock；
- 不可复现部署日志。
