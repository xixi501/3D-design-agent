# 演境工作台独立用户体验验收说明

> 给另一个 Agent 的验收任务。  
> 你的角色是“第一次使用这个产品的真实用户”，不是代码审计员。  
> 请通过实际浏览器操作发现问题，不要只读文档、不要只调用 API。

## 1. 目标

验证普通用户能否在工作台里顺畅完成：

1. 打开项目 / 看懂当前空间；
2. 编辑、撤销、保存；
3. 查看 3D / 漫游；
4. 看懂检查结果；
5. 对可修复问题发起 AI 修复；
6. 理解哪些问题不能被 AI 修复；
7. 在移动端完成关键操作。

重点不是“功能是否存在”，而是：

- 用户是否知道下一步该点什么；
- 点击后是否真的发生预期行为；
- 文案是否与实际行为一致；
- 是否出现死路、假成功、无法撤销、计数矛盾；
- 页面是否报错或卡住。

## 2. 环境

工作台已经启动，使用当前 `dev/core@6f5dc9b` 和干净临时数据：

```text
http://127.0.0.1:3001/
```

如果页面打不开：

1. 先检查服务：`curl -s http://127.0.0.1:3001/api/health`
2. 如果服务正常但浏览器打不开，这是端口/网络映射问题，不是产品 bug；记录下来并停止，不要自行重建数据。
3. 如果你与工作台不在同一执行环境，需要端口转发 3001；不要用旧的 3020 演示实例。

当前只预置了 4 个体验项目，项目名都以“体验 ·”开头：

| 项目 | URL |
|---|---|
| 全屋样板间 | `http://127.0.0.1:3001/?project=43420091-ec5a-4c90-878e-f997efe2af0e` |
| 结构问题 | `http://127.0.0.1:3001/?project=ac2ea03e-63de-40cd-96c0-5b02000b2f82` |
| 净空修复 | `http://127.0.0.1:3001/?project=d6737cd5-3707-42f9-85ac-20b51e0a8ea1` |
| 客餐厅基准 | `http://127.0.0.1:3001/?project=d5d73080-d843-4e9f-b4ae-18614fe605a0` |

这些项目使用临时数据；你可以操作、撤销、触发 AI 修复，但不要清空数据库或修改代码。

## 3. 操作方式

- 使用真实 Chromium/Chrome，通过鼠标点击、键盘输入、滚轮、拖拽操作。
- 可以用浏览器自动化驱动，但必须模拟真实用户操作，不能只用 `fetch("/api/...")` 判断 UI。
- 每次重要操作前后截图，保存到：

```text
test-results/ux-agent/<timestamp>/
```

- 记录：
  - 页面 `pageerror`；
  - Console error；
  - 失败的请求（4xx/5xx）；
  - 操作步骤；
  - 预期 vs 实际；
  - 截图路径。
- 不要修改产品代码、不要改测试、不要提交 Git。
- 不要先阅读既有审计报告；先独立体验，最后再决定是否需要对照。

## 4. 验收任务

### 任务 A：首次进入与项目画廊

1. 打开 `http://127.0.0.1:3001/`。
2. 观察第一眼：是否知道这是 AI 空间设计工具、下一步能做什么。
3. 点击“打开项目”。
4. 检查：
   - 是否看到 4 个“体验 ·”项目；
   - 是否错误显示 `Evaluation only` 或“2BHK 样板间”；
   - 项目卡片是否可读、可点击；
   - 空项目、当前项目是否造成列表混乱。
5. 关闭画廊，确认回到工作台没有异常。

记录：首屏理解成本、命名、空状态、卡片可读性、是否需要滚动/寻找。

### 任务 B：全屋样板间

打开“体验 · 全屋样板间”。

检查：

1. 概览是否显示 4 个空间、14 件家具、版本；
2. 待处理数量是否与检查面板一致；
3. 3D 视图是否真的渲染出空间；
4. 漫游能否进入、移动、退出；
5. 空间导航是否可用；
6. 导出 PNG / 打印 PDF 的入口是否可发现（可以只检查按钮和提示，不要求真的打印）；
7. 有没有明显的空房间、白墙盒子或不知道为什么这样布局的感觉。

重点：这是展示样例，用户会不会误以为“任意全屋都能做到这样”。

### 任务 C：结构问题

打开“体验 · 结构问题”。

检查：

1. 概览是否提示有问题；
2. 检查面板是否标为“结构”；
3. 是否有“AI 修复”按钮；如果没有，用户是否知道为什么；
4. 点击检查项，是否能定位到门/墙，而不是错误选中家具；
5. “去结构编辑”是否真的打开结构工具；
6. 页面上是否有“自动修复一定能解决”的暗示。

重点：用户是否理解“这个不是家具 Agent 能修的”。

### 任务 D：净空修复

打开“体验 · 净空修复”。

这是一个允许调用真实 DeepSeek Agent 的案例。操作：

1. 从概览点击“一键修复”，或点击卧室的“修复”；
2. 阅读确认框；
3. 确认后等待真实 Agent 完成，通常需要几十秒；
4. 观察任务阶段、进度文案、是否卡住；
5. 完成后检查：
   - 结果卡是否显示真正结果；
   - 项目检查是否变为 0；
   - 目标家具是否移动；
   - 是否只改了授权家具；
   - 撤销后是否恢复原状；
   - 是否出现“检查通过”但实际仍有问题的情况。
6. 如果失败，记录错误文案、任务状态、是否可重试，以及用户在 UI 上能不能理解失败原因。

注意：这一条会消耗真实 API；只做一次完整尝试即可。

### 任务 E：普通编辑

打开“体验 · 客餐厅基准”。

检查：

1. 选中家具 → 拖动 → 旋转 → 撤销 → 重做；
2. 保存状态是否明确；
3. 切换 2D / 分屏 / 3D；
4. 进入漫游、移动、退出；
5. 检查面板是否与概览一致；
6. 添加家具、属性编辑是否可用；
7. 打开/关闭柜门或门扇是否可从 UI 发现。

重点：不要只看“按钮存在”，要看操作是否顺畅、是否误触、是否能撤销。

### 任务 F：空项目与新建

点击“新建空间”。

检查：

1. 空状态是否告诉用户下一步；
2. “从一句话开始”和“上传户型图”是否可用/可理解；
3. 没有内容时是否错误显示全屋检查或漫游；
4. 关闭/返回是否丢失已打开项目。

### 任务 G：移动端

在 390×844 宽度下检查：

1. 工作台是否可用；
2. AI 舱、属性抽屉、项目画廊是否打得开；
3. 是否出现横向溢出；
4. 关键按钮是否被遮挡；
5. 3D/漫游是否至少可查看。

## 5. 发现问题的判定

按用户影响分级：

- **P0**：无法完成主流程、数据丢失、误提交、假成功、无法撤销。
- **P1**：明显误导文案、主要流程死路、结构/家具修复边界让人误解。
- **P2**：操作摩擦、信息层级混乱、移动端不可用但非完全阻断。
- **P3**：视觉、文案、细节问题。

每条问题必须包含：

```text
标题：
严重度：
项目/URL：
操作步骤：
预期：
实际：
证据：截图路径、Console、网络请求
影响：
建议：
```

不要把“我猜代码里可能有问题”当作已验证问题；只报告你在工作台实际观察到的行为。

## 6. 输出

在以下目录写报告：

```text
test-results/ux-agent/<timestamp>/report.md
test-results/ux-agent/<timestamp>/report.json
```

报告结构：

1. 总体结论：能否完成 7 个任务；
2. 已确认可用；
3. 问题清单（按 P0 → P3）；
4. 每个问题的复现步骤和证据；
5. 无法判断/受环境限制的部分；
6. 最影响首次使用体验的 3 个问题。

不要修改或提交任何 Git 文件；只写 `test-results/`。

## 7. 时间与安全

- 建议 60–90 分钟。
- 真实 Agent 修复只做一次完整尝试，避免无意义消耗。
- 不要访问 `.env`、不要输出密钥、不要把工作台暴露到公网。
- 如果服务/浏览器/端口不可用，先报告环境阻塞，不要假定是产品缺陷。

## 8. 当前边界

- 这是干净的临时数据实例，不是用户真实数据。
- 全屋 showcase 是 4 房间样例，不是任意 9 房全屋。
- 真实户型图 VLM、照片转 3D、AgentArts 云不在本次验收范围。
- 你的任务是找“用户实际体验问题”，不是重复代码审计。
