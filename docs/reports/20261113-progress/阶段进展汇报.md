# 演境 ActiScape：项目阶段进展汇报

2026 年 11 月 13 日

## 一、我们想做什么

我们希望做一个面向普通用户的室内设计助手。用户可以通过自然语言描述空间和使用需求，得到可编辑的三维房间，并通过对话或手动操作持续调整，最后保存和重新打开方案。

我们计划逐步支持文字、户型图和物品照片等输入：文字用于表达设计需求，户型图帮助建立空间结构，物品照片用于生成可放入场景的三维资产。设计结果要能够检查、修改和保存。

## 二、目前进度

### 一：主系统、工作台与 Agent 协作

已经形成可操作的二维／三维工作台，支持选择家具、调整属性、导入 GLB、保存项目、撤销和重做。用户可以选中家具后通过对话移动、旋转、修改尺寸和颜色，也可以进行受约束的新增家具与局部布局。

在自然语言生成方面，目前支持从文字生成一个矩形空间及基础家具布局，覆盖客餐厅、阅读会客间、主卧、次卧、书房、厨房、卫生间、玄关和过道九类。缺少关键尺寸或门窗信息时会补问。执行 Agent 对九类各做两次真实生成自测，**18/18 通过固定样例的既定检查**；独立复验暂缓。已有场景编辑阶段已验收，本轮还完成了 16/16 编辑回归案例。

技术上，主控理解需求并按需调度资产选择、布局设计和检查角色；尺寸、坐标、数量和修改范围由代码核对，候选通过检查后保存，支持撤销和继续编辑。户型图方面已有识别、标定、草稿校正流程和历史成功样例，但当前真实户型导入仍需完善。

当前边界：文字生成主要面向单个矩形空间，多房间联动、不规则房间和施工级设计尚未完成。现场将演示工作台与已有场景的对话修改。

### 二：照片生成三维物品

已开发独立的照片转 3D 资产服务，支持上传照片、生成任务、GLB 下载和尺寸校准。已有一个 V100 真实花瓶生成案例：正面轮廓和主要颜色可辨，但背面存在黑色区域与纹理问题，外观尚需改善。新版代码加入了贴图前减面、模型归一化和缓存等能力。

11 月 13 日的分支交接记录说明，Hunyuan 服务已部署在学校 GPU 环境，并提供通过平台转发的地址；已有任务查询与旧模型下载的验证记录。**主系统尚未完成远端联调，当前也没有新版减面管线的完整真实生成验收。**

### 三：设计知识与部署适配

已整理设计 Skill 池，将房间布局、风格、照明、户型接收和检查修复等知识组织为结构化内容。主系统当前代码索引共 33 个 Skill，其中 17 个处于启用且已验证状态、16 个为预留；系统按任务选择适用知识，不能将预留内容当作已验证能力。

平台部署方面已有本地运行适配与验证基础，**真实华为云 AgentArts 完整部署和端到端联调尚未完成**，后续需要结合实际平台环境继续验证。

### 我们目前的多 Agent 架构与运行框架

这里的 Harness 是我们围绕模型建立的一套**任务运行、约束和恢复机制**，不只是给模型的一段提示词。当前主系统由工作台、场景服务和 Agent 服务组成：工作台负责交互，场景服务负责项目、候选、检查与保存，Agent 服务组织模型角色和任务流程。系统基于 LangGraph 编排，任务及事件保存在本地数据库，流程检查点使用 SQLite。

系统按“用户交互 → 代码调度 → 角色协作 → 检查保存”组织。Policy 是代码规则路由器，Harness 是任务运行框架；模型角色主要有以下四类：

| Agent | 当前代码角色 | 负责什么 |
| --- | --- | --- |
| 需求理解 Agent | `main`，执行 `ground` | 理解用户意图、识别缺失信息、形成结构化需求 |
| 资产选择 Agent | `assets` | 查找家具与模型，匹配用途、规格和数量，输出资产候选 |
| 空间设计 Agent | `design` | 根据要求安排家具位置与朝向，生成或修复布局候选 |
| 独立检查 Agent | `check` | 结合需求、代码检查结果和场景截图，给出问题或通过意见 |

这些是按需调用的模型角色，不代表四个常驻进程，也不要求每次任务全部参与。代码负责任务分发、授权、候选预检、按需渲染和最终提交；明确的精确编辑可走代码快捷路径。户型图还包含专门的结构识别、测量与草稿确认步骤。


| 图中路径 | 何时进入 | 如何执行 |
| --- | --- | --- |
| 文字生成 | 显式生成模式，或文字包含生成意图、房型及尺寸词 | 需求 Agent 明确并冻结尺寸、门窗和家具要求 → 资产 Agent 匹配家具 → 登记初始化授权、设计 Agent 提出布局 → 代码预检、渲染、检查 Agent 审核 → 提交保存 |
| 户型重建 | 携带户型图，或显式户型模式 | 结构识别与测量 → 草稿校正和用户确认 → 资产匹配及布局候选 → 代码和图像检查 → 提交保存；图中概括了不同版本的专用处理步骤 |
| 场景编辑：精确操作 | 编辑任务中有明确的移动、旋转、尺寸或颜色要求等 | 优先代码解析，无法确定时由需求 Agent 理解 → 授权与代码计算 → 确定性候选检查 → 提交；不必调用设计 Agent |
| 场景编辑：新增／局部布局 | 需要增加家具或重新安排局部空间，或显式布局修复 | 需求 Agent → 按需资产 Agent → 授权与设计 Agent → 代码预检、按需渲染和检查 Agent → 提交 |
| 门柜／电器动作 | 简单开关指令且目标明确，或显式动作模式 | 代码解析目标与状态 → 动作候选 → 确定性检查 → 通过后提交；失败通常等待用户 |
| 照片资产入场 | 已有照片资产 ID，或显式照片入场模式 | 读取已有模型 → 计算地面／台面落位 → 候选与确定性检查 → 通过后提交；照片生成由独立服务承担，主系统联调尚未完成 |
| 等待输入 | 目标不唯一、资料缺失或无法安全执行 | 返回问题 → 用户补充 → 恢复任务，重新核对要求后继续 |

图的阅读说明：Policy 先检查户型图和显式模式，普通请求再依次匹配简单动作、文字生成和照片放置意图，其余进入编辑。精确操作与局部布局是编辑任务内部的分支；“等待输入”表示暂停后的结果状态。图按用户任务展开，实际代码会复用候选检查、审核和提交节点。

检查不通过时，文字生成和布局设计可以按问题有限返回资产选择或设计；达到预算上限或需要用户确认时停止。确定性候选使用代码审核，需要视觉判断的候选才渲染检查图并调用检查 Agent。提交时核对候选哈希、基准版本和固定操作 ID。

Skill 按任务和阶段提供知识；本地任务通过 SQLite 检查点、事件、候选及操作 ID 支持追踪和恢复。照片转 3D 远端服务尚待主系统联调，云端多实例恢复仍待验证。

### Skill 池如何接入系统

Skill 是按统一结构组织的设计经验和判断要求，例如空间通行、房型家具布置、风格一致性和布局修复。每项包含适用范围、能力要求、内容、判据以及版本和状态；Skill 提供设计与检查依据，**不直接获得修改或提交场景的权限**。

当前代码中的 Skill 索引共 **33 项：17 项 active 且 verified，16 项 reserved**。这里的 verified 是相应 Skill 的既有验证状态，不能推断覆盖所有房型或所有真实需求；预留项不会进入正常候选短名单。

在接入 Skill Bundle 的设计流程中，实际方式是：

1. **通用基础。**系统加载 `universal-spatial-base`，为空间设计提供共同的基础要求。它会按阶段截取相关内容，不是每个任务、每次模型调用都注入完整正文。
2. **按任务选择。**代码先根据任务模式、项目状态、房间类型、面积及能力等筛选已启用候选；模型只能在短名单中选择一个主 Skill，并可选择最多两个补充 Skill，例如风格一致性或照明配色。
3. **按阶段注入。**资产选择、设计、检查、修复等阶段只接收相应的知识切片。户型接收流程可注入 intake Skill；检查失败后才启用预先冻结的修复 Skill。纯代码的精确操作不必调用所有角色或 Skill。
4. **固定任务快照。**任务记录选择结果、内容和哈希；同一需求恢复时沿用快照，用户改变需求时重新判断适用性。旧任务保留对旧快照的兼容读取，避免运行中更新知识造成同一任务前后不一致。

目前照片资产相关 Skill 虽在代码索引中为 active／verified，**真实照片服务尚未与主系统完成端到端联调**；单项知识的状态不能替代完整产品能力验收。

### Skill 池后续如何维护和丰富

现有机制支持为 Skill 标记版本、适用条件、能力、判据和启用状态，更新后通过固定快照同步到主系统；预留内容需要相应验证后再启用。

下一步计划结合设计资料、失败案例和用户反馈，补充不同房型、使用关系和风格约束，并为每项补充适用边界、来源、正反案例及可检查的判据。新内容先离线检查结构和引用，再通过真实场景中的候选检查与边界案例，确认效果后再启用；保留版本、结果与失败案例，避免只增加知识数量而无法评估质量。更系统的专家评价、用户试用及自动优化仍属于后续工作。

## 三、发现的问题和困难

1. 模型结果的可靠性。模型可能遗漏家具、误判朝向或给出不合适的尺寸和布局。需要同时检查用户要求、几何关系和实际画面；现有检查还没有覆盖全部通行、精确网格碰撞及法规问题。
2. 真实户型的结构还原。户型图识别可能漏墙、产生碎墙，或出现墙端连接、门窗归属、尺寸与坐标不一致的问题。历史样例的成功不代表任意图片都能稳定导入，当前旧版回放仍有失败项。
3. 照片生成的质量和尺寸。单张照片看不到物品背面，也无法直接得到真实尺度；生成模型可能有纹理缺陷，需要用户查看并确认尺寸。新版轻量化结果还需真实验证。
4. 多模块联调与运行耗时。真实照片生成耗时较长，远端服务、网络、鉴权、任务状态和中断恢复都需要联合验证。当前主系统接入的旧接口与成员二最新版接口仍需对齐。
5. 设计知识与评价。Skill 有助于组织设计经验，但规则覆盖有限；现有固定案例还不足以证明不同房间、真实用户需求下的设计质量与使用体验。

6. **自由设计授权理解不足，导致反复补问。**实际使用中，用户要求生成 20 米 × 10 米的现代东方餐厅，包含圆桌、方桌和窗户，并多次明确让系统决定其余布局、数量和位置；系统仍持续追问入口与窗户的墙面和位置，未能推进设计。这说明现有需求处理还不能充分区分“信息未说明”和“用户授权系统自主决定”。详见[实际问题记录](问题记录_自由设计授权未识别.md)。

## 四、后续计划

1. 接入成员二远端资产服务。对齐接口和身份验证，完善任务状态、错误提示及尺寸确认；完成“上传照片 → 生成模型 → 预览和校准 → 放入房间 → 保存、撤销和重开”的联合验证。
2. 完善真实户型辅助导入。统一结构坐标和几何编译，重点处理墙体连接、门窗归属、尺寸标定与原图对照，允许用户进行必要的确认和修正。
3. 持续提升设计与编辑可靠性。补充真实使用案例，完善对用户明确要求、家具使用关系和异常情况的检查；自然语言生成的独立复验暂缓，之后再安排。
4. 完善 Skill 与部署联调。逐步验证和启用设计知识，结合实际平台完成任务恢复、服务部署与端到端测试。
5. 建立更贴近使用的评价方式。在现有功能和固定案例测试之外，讨论加入不同户型、设计合理性评价及用户试用反馈。
6. **完善自由设计的需求与授权机制。**识别“你看着办、按你的审美”等委托意图，将硬约束与可自主决定项分开，在授权范围内提出方案并说明设计决定；补充多轮对话测试，避免重复补问已授权参数。
