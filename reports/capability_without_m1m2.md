# 只有成员3：能做到什么程度

> 2026-11-08 · 回答"先不要成员1、2 的工作能做到什么程度"
> 全部结论都附本机实跑证据；没有证据的地方写"未验证"。

## 0 一句话

**能到"接口契约级的端到端"，到不了"产品级"。**
具体说：技能包可以脱离成员1 的场景服务被 HTTP 真实执行（建场景 → 提交修改 → 检查 → 出平面图 → 判定通过/失败），AgentArts 运行时可以真实调用这条链路；但"读懂用户一句话 → 选技能 → 生成修改"这一环仍是**数据回放**，不是模型推理——那一环属于成员1 的编排。

## 1 能力阶梯（现在实际站在第 3 层）

| 层 | 内容 | 依赖谁 | 现在状态 | 证据 |
|---|---|---|---|---|
| L0 内容 | 判据库、技能包、案例 | 无 | ✅ 完成 | `skills/` 22 包、判据 60 条 |
| L1 结构验证 | frontmatter/manifest/引用/禁用词/案例齐备 | 无 | ✅ 22/22 | `reports/lint.json` |
| L2 几何验证 | 自建几何引擎跑 44 案例，正反向断言 | 无（自建替身） | ✅ 44/44 | `reports/dry_run.json` |
| L3 契约验证 | 按 `TOOLS.md` 起一个**场景服务**，44 案例全走 HTTP | 无（自建替身） | ✅ 47/47（44 案例 + 3 条系统语义） | `reports/http_cases.json` |
| L3+ 端到端 | AgentArts 运行时 → `skill.execute` → 场景服务 → 检查 → 平面图 | 无（自建替身） | ✅ 12/12（含正向/边界/出图） | `reports/smoke_s0_e2e.json`、`reports/smoke_s0_e2e_http.json` |
| L4 平台 | 真上云（镜像构建 + 部署 + 平台日志） | 账号 + Docker | ⛔ 未做 | `versions.json.runtime` 仍为 null |
| L5 产品 | 真户型解析、3D/漫游、照片→GLB、多 Agent 编排、真人验收 | 成员1、2 | ⛔ 做不了 | — |

## 2 L3 到底证明了什么、没证明什么

**证明了：**
1. `TOOLS.md` 的契约是**可实现**的：`scene.get_snapshot / apply_edits / diff / check.run / view.capture` 六个动作能构成闭环，返回值够用；
2. 技能案例是**可执行资产**，不是文档：44 个案例（含 22 个边界）在服务化形态下逐条跑出预期结论；
3. 系统语义能落地：版本冲突被拒（`E_VERSION_CONFLICT`）、同 `op_id` 幂等、`scene.diff` 能指出新增对象；
4. 平台侧入口能真实调工具：SDK 运行时（uvicorn）收到 `/invocations` 后，跨进程 HTTP 调场景服务，再返回判定与 PNG。

**没证明（重要，别当成已完成）：**
1. **没有"理解用户"这一环**。`skill.execute` 回放的是案例里预置的 `edits`，它不读自然语言、不选技能、不生成修改。技能正文（"先定主墙，再压通道"）对模型是否真的有用，**没有测过**；
2. **几何引擎是我写的替身**，不是产品检查器。判据口径与真实实现一致与否，要等成员1 对照；
3. **场景模型极小**：矩形墙 + 洞口 + 家具包围盒，没有斜墙、多楼层、自由模型、材质；
4. **渲染是示意图**，不是产品 3D；
5. **没有真人用**：好看、好用、适老/宠物体验全部未测。

## 3 为什么这些替代品不会白做

三个约束保证"换真的不返工"：

1. **契约同源**：mock 服务的接口就是 `TOOLS.md`，成员1 换真实现时，我这边只改 `SCENE_SERVICE_URL`，技能、案例、smoke 一律不动；
2. **口径同源**：mock 的几何判定复用 `tools/mockscene.py`，和 dry-run 是同一套；技能案例不会出现"mock 过、真的不过"的两套标准（真实现若有差异，差异本身就是要对的账）；
3. **证据同格式**：`reports/http_cases.json` 与平台 smoke 的报告结构一致，S1 接真工具时可以直接对比"同一批案例两边结论是否一致"——这正是 L3 到 L4 的验收方式。

## 4 还能继续推进的（不需要成员1、2）

按"价值/成本"排序：

| 优先级 | 事项 | 说明 | 估时 |
|---|---|---|---|
| 1 | **全量技能走契约执行** | 现在 `skill.execute` 只跑了 2 个案例；扩成 44 个（改一个循环即可），让每个包都有"HTTP 可执行"证据 | 0.5 天 |
| 2 | **确定性技能选择器（替身）** | 用 `manifest.applies_when` 做规则选择，证明"22 个技能能被正确区分"；策略最终归成员1，但可以先给出可评估的选择基线 | 1 天 |
| 3 | **多轮局部修改语义** | 在契约层跑"只改阅读角"：`apply_edits` + `scene.diff` 证明无关对象未变（对应设计书 §3.3、J-VER-01） | 1 天 |
| 4 | **资产服务替身（assets.*）** | 把照片导入流程也跑到契约级：作业状态机、`scale_calibrated`、失败不改场景 | 1 天 |
| 5 | **一致性测试套件** | 把 44 案例做成"真实现 conformance 包"，成员1 接工具时直接跑，不一致就出差异报告 | 1 天 |
| 6 | **演示脚本** | 一条命令生成"技能 → 场景 → 检查 → 图"的演示材料（答辩/周会用） | 0.5 天 |

**做不了的（缺的不是时间，是别人的东西）**：真户型图解析、3D/漫游、照片→GLB、LangGraph 多 Agent、真实用户验收、S1–S5 阶段验收里"真实集成"的部分。

## 5 给团队的三句话

1. **接口可以现在冻结**：`TOOLS.md` 已经被 44 个案例+端到端跑过一遍，成员1 按它实现即可，改动成本比现在低；
2. **验收标准可以现在定**：同一批 44 案例，真实现跑出的 `pass/codes` 必须与替身一致（不一致就查是口径差异还是实现 bug），这比"看起来能用"硬；
3. **成员3 的边界仍然清楚**：我做的是测试替身与验证件，不是产品；`mock/` 目录的 README 第一行就写了"这不是产品"。

## 6 复现命令

```powershell
$env:PYTHONIOENCODING='utf-8'
# 1 技能池
python tools/skill_lint.py
python tools/dry_run.py --all
# 2 契约级（44 案例走 HTTP）
python mock/run_cases_http.py
# 3 端到端（运行时 → 技能 → 场景服务 → 检查 → 图）
$env:SCENE_SERVICE_URL='http://127.0.0.1:8100'
python deploy/smoke.py --local --with-scene
# 4 平台运行时（需 SDK venv）
python -m agent        # 在 deploy/ 下，AGENT_RUN_PORT=8099
python deploy/smoke.py --base http://127.0.0.1:8099 --with-scene
```
